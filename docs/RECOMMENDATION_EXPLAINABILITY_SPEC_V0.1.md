# EDpj Recommendation Explainability Specification

**Version:** 0.2  
**Status:** Phase 2 Design Baseline  
**Date:** 2026-09-05  
**Previous:** 0.1 — Confidence / freshness / ReasonFact / DataSource baseline

## 1. Design Principle

### Every Recommendation Must Be Explainable

EDpj must be able to trace every recommendation from source data through deterministic calculation to the final recommendation.

The responsibility boundary is:

```text
External/Game Data
        ↓
Local DB / Facts
        ↓
Python Deterministic Calculation
        ↓
Recommendation + Reason Facts
        ↓
Claude / AGY (optional)
        ↓
Natural-language narration only
```

LLM output is never authoritative for facts, numeric calculation, candidate filtering, ranking, confidence, or recommendation selection.

The CLI must remain fully functional without an LLM.

## 2. Recommendation DTO

Phase 2 recommendation output must contain at least:

```python
class Recommendation:
    action: str
    target: BioTarget | MiningTarget
    expected_value: float
    action_horizon_seconds: float
    score_per_hour: float
    confidence: float

    breakdown: dict[str, HorizonComponent]
    data_sources: list[DataSource]
    reasons: list[ReasonFact]
    rejected: list[RejectedCandidate]
    narration: str | None
```

`narration=None` is valid. The recommendation must remain complete and explainable without LLM-generated text.

## 3. Deterministic Reason Facts

`reasons[]` must be generated by Python, not by Claude/AGY.

```python
class ReasonFact:
    factor: str
    effect: str       # positive | negative
    value: float
    comparison: float | None
```

`factor` identifies the deterministic factor, for example:

- `score_per_hour`
- `expected_value`
- `action_horizon`
- `travel_time`
- `market_price`
- `demand_penalty`
- `data_freshness`
- `market_stability`
- `model_applicability`
- `confidence`

`effect` is also determined by the calculation layer. LLM must not decide whether a factor is positive or negative.

The same calculation input must produce the same `ReasonFact` set, independent of whether an LLM is available.

## 4. Rejected Candidates

Rejected candidates are divided into two categories.

### 4.1 Filter exclusion

A candidate is removed before ranking because it violates a deterministic condition.

Examples:

- demand is zero / invalid for the required action
- landing pad is incompatible with the ship
- jump range is insufficient
- required data is unavailable
- destination is otherwise unreachable
- a required price model is not applicable to the observed market condition

The rejection reason is deterministic and should be recorded as a structured fact.

```python
class RejectedCandidate:
    category: str       # filter | score
    action: str
    target_id: str
    reason_code: str
    value: float | None
    comparison: float | None
```

### 4.2 Score loss

The candidate passed all filters but ranked below the selected candidate.

Score-loss records must contain the numeric comparison. They do not need to enumerate every losing candidate in the UI.

Phase 2 UI should normally expose only the top few score-loss alternatives while retaining the deterministic records internally for debugging/audit.

Example:

```text
Mining / Station A
score = 35.7M Cr/h
selected candidate = 42.1M Cr/h
reason = LOWER_SCORE
```

## 5. Unavailable Time Components

`unavailable` must never silently become zero and must never be replaced by an undocumented constant.

For every unavailable component, the recommendation must expose:

```text
status       = unavailable
used_value   = explicit policy result
confidence   = resulting value
basis        = why the value/policy was selected
```

There are only valid ways to handle an unavailable component:

1. **Exclude the candidate from scoring** when the component is mandatory.
2. **Use an explicitly specified fallback estimate** when the specification defines one.
3. **Present the candidate separately as incomplete/uncertain** when scoring is intentionally allowed without that component.

The implementation must never silently do:

```python
unavailable_seconds = 0
```

If a future specification defines a fallback such as:

```text
supercruise = 4.0 min fallback
confidence penalty = -0.15
```

both the fallback value and penalty must be represented in the recommendation breakdown and ReasonFact list. They must be constants defined by the deterministic calculation layer, not invented by the LLM.

Current Phase 0-C behavior remains unchanged: candidate-specific supercruise prediction is `unavailable` because the current data sources do not provide actual SC travel distance. The fallback/scoring policy itself is a Phase 2 decision.

## 6. Confidence Composition

Phase 2 must define a deterministic confidence composition rule before confidence is exposed as a recommendation-level number.

The baseline candidate for implementation is multiplicative composition:

```text
confidence = Π(component_confidence)
```

Initial component status mapping:

```text
measured      = 1.00
estimated     = 0.85
unavailable   = 0.60
```

These values are configuration constants, not LLM decisions.

Data freshness must also affect confidence through a deterministic freshness factor:

```text
final_confidence
 = component_confidence_product
 × freshness_factor
```

The freshness factor must be defined per data class/source. At minimum, market observations must decay with age so that a materially stale market does not receive the same confidence as a fresh observation.

### 6.1 Market Stability is not a score multiplier

Historical market stability is an **applicability diagnostic**, not an expected-value or score multiplier.

Do not implement:

```text
score_per_hour
 = expected_value × stability_factor / horizon
```

or any equivalent implicit price discount based only on volatility.

Instead:

```text
Historical EDDN
      ↓
Market Stability
      ↓
Model Applicability
   ┌──┴──────────┐
   ↓             ↓
APPLICABLE   NOT_APPLICABLE
   ↓             ↓
normal model   do not present price prediction as reliable
```

A `VOLATILE` classification does not mean that a fixed percentage should be subtracted from the expected value. It means the historical evidence may be insufficient to justify applying the price model at all.

`INSUFFICIENT` means unknown, not stable.

### 6.2 Historical validation

Market stability thresholds must be derived and validated using historical EDDN observations. The objective is to verify that markets classified as volatile actually exhibit materially worse prediction error, or else revise the classification rule.

The system must not claim that volatility predicts model failure without backtest evidence.

The calculation layer must retain enough metadata to explain confidence reductions, for example:

```text
confidence = 0.61

components:
  travel_time: measured      1.00
  mining_cycle: estimated    0.85
  market: measured           1.00

freshness:
  market: 0.72

1.00 × 0.85 × 1.00 × 0.72 = 0.612
```

Any additional confidence cap or aggregation rule must also be deterministic and visible in the breakdown.

## 7. Historical Replay / Backtest

Phase 2 explainability validation must distinguish deterministic ranking correctness from real-world usefulness.

Historical replay uses past market observations and, where available, the user's own Journal-derived state.

```text
State at T0
   ↓
EDpj prediction
   ↓
predicted_value
predicted_horizon
predicted_rank
   ↓
T0 + predicted_horizon
   ↓
observed outcome
   ↓
prediction vs actual
```

The replay must prevent future leakage: observations after T0 must never influence the T0 input state.

EDDN-only replay validates market/ranking behavior; it does not prove the user's realized profit because another player may have generated the observation. User Journal/Credits/Cargo/sale events are required for direct realized-profit validation.

The primary practical evaluation is not extreme precision of the horizon denominator. It is whether the value predicted for an action is reasonably reflected by the actual outcome after the predicted horizon.

Minimum metrics:

```text
prediction_count
applicable_count
insufficient_count
predicted_value
actual_value / actual_delta
absolute_error
relative_error
rank_at_T0
actual_best_outcome
```

## 8. LLM Contract

Claude/AGY receives only the structured recommendation, deterministic ReasonFacts, breakdown, and relevant source/freshness metadata.

The prompt must explicitly require:

- do not introduce facts absent from the supplied data
- do not introduce numeric values absent from the supplied data
- do not alter the recommendation
- do not alter ranking
- do not recalculate the score
- explain only the supplied ReasonFacts and breakdown

The LLM output is `narration` only.

A post-generation validator should extract numeric tokens from `narration` and verify that every material numeric value is present in the supplied structured input, allowing only explicitly permitted formatting transformations such as commas, units, and rounding.

If validation fails, narration must be discarded and the deterministic recommendation must still be shown.

## 9. Explainability UI

The UI must expose at least:

```text
Recommendation
 ├─ Score / hour
 ├─ Expected value
 ├─ Action horizon
 │   └─ per-segment measured / estimated / unavailable
 ├─ Confidence
 │   └─ component + freshness contributions
 ├─ Market stability / model applicability
 ├─ Why selected?
 │   └─ ReasonFacts
 ├─ Why others lost?
 │   ├─ filter exclusions
 │   └─ top score-loss alternatives
 └─ Data sources / freshness
```

The UI must not require narration to explain the recommendation.

## 10. Phase 2 Exit Criteria

Phase 2 explainability is complete only when all are true:

- every recommendation has deterministic `ReasonFact` records
- filter exclusions and score losses are distinguishable
- every unavailable time component has an explicit handling policy
- recommendation-level confidence is mechanically reproducible
- freshness affects confidence through named deterministic rules
- market stability is evaluated from historical data
- market stability is not used as a score multiplier
- volatile markets are not presented as reliably price-predictable without historical evidence
- historical replay prevents future leakage
- CLI produces a complete recommendation without LLM
- LLM narration can be omitted without loss of decision information
- LLM narration is validated against supplied structured facts
- identical inputs produce identical recommendation, reasons, confidence, and ranking

## 11. Relationship to Phase 0-C

This document does not change the Phase 0-C decision that current Journal-derived supercruise duration is observed telemetry only.

In particular:

```text
SC duration observed in Journal
        ≠
SC travel-distance model
```

A future data source that supplies actual SC travel distance may move the SC component from `unavailable` to `estimated`. That transition must be visible in the recommendation breakdown and confidence calculation rather than silently changing behavior.
